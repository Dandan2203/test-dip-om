# Архітектура FinAgent

## Шари
**Backend (Go, Clean Architecture):**
- `domain` — сутності та інтерфейси (порти).
- `usecase` — бізнес-логіка.
- `repository` — доступ до PostgreSQL (sqlx).
- `delivery/http` — Gin-хендлери, middleware (auth, rate-limit, logger).
- `ai` — клієнт до Python AI-сервісу.

**AI-сервіс (Python, FastAPI):** ендпоінти `/chat`, `/categorize`, `/audit`. Модель — Anthropic Claude Haiku 4.5.

## Потік чату (нативний tool-use)
Користувач → `POST /api/chat` (JWT) → бекенд збирає контекст (транзакції/цілі/категорії) → `POST /chat` AI-сервісу (shared-secret) → `agents/chat.py`:

1. Один виклик Claude з набором інструментів:
   - **read-tools** (`get_balance`, `get_top_expenses`, `simulate_purchase`, `get_goals_progress`) — виконуються в Python над контекстом; результат повертається моделі, модель формує відповідь.
   - **action-tools** (`create_transaction`, `delete_transaction`, `create_goal`, `contribute_goal`, `withdraw_goal`, `delete_goal`) — лише ЗАХОПЛЮЮТЬ намір; повертаються бекенду як `ActionData`.
2. Інтент визначається з обраного шляху (ACTION / SCENARIO / FINANCIAL / GENERAL) — окремого виклику-класифікатора немає.
3. Бекенд зіставляє дію з реальними сутностями користувача й повертає `pendingAction` із текстом підтвердження.
4. Користувач підтверджує → `POST /api/actions/execute` → дія виконується й пишеться в `action_log` (для `POST /api/actions/undo`).

Було: окремий виклик-роутер + ReAct-агент + ручний парсинг JSON. Стало: один виклик, типізовані інструменти, нуль ручного парсингу. Окремі `contribute_goal`/`withdraw_goal` прибрали потребу в хардкод-списку слів.

## Дані та приватність (data-flow)
- У чат-модель потрапляють: текст повідомлення користувача та **агрегати** з read-tools (суми, топ-категорії, прогрес цілей). Сирі описи транзакцій у чат-модель не передаються.
- `/categorize` та `/audit` отримують описи транзакцій — вони делімітовані як дані (захист від prompt-injection: модель інструктована не виконувати команд із них).
- Anthropic за замовчуванням не використовує дані API для навчання.
- Лог `ai_chat_logs` зберігає лише текст повідомлення, інтент і текст відповіді (без сум/категорій/цілей).
- **Ретенція**: рекомендована політика — видаляти записи старші за 90 днів (напр. плановим завданням: `DELETE FROM ai_chat_logs WHERE created_at < now() - interval '90 days'`). Для демо не автоматизовано.

## Безпека
- **AI-сервіс приватний**: порт назовні не публікується; кожен запит вимагає заголовок `X-Internal-Token` (= `INTERNAL_API_TOKEN`); CORS прибрано (звертається лише бекенд).
- **Секрети обов'язкові** (fail-fast при старті): `JWT_SECRET`, `ENCRYPTION_KEY`, `AI_INTERNAL_TOKEN`/`INTERNAL_API_TOKEN`, `ANTHROPIC_API_KEY`, `DATABASE_URL`. Дефолтних значень немає.
- **Mono-токени** — AES-256-GCM (`internal/pkg/crypto`).
- **Авторизація** — JWT; бізнес-маршрути за `Auth`-middleware; перевірка власника сутностей (`userID`).
- **Rate-limit** — глобальний 20/с (burst 40) + окремий суворіший 1/с (burst 5) на AI-маршрути (`/chat`, `/anomalies`, `/mono/import`).
- **Захист дій** — human-in-the-loop підтвердження + `action_log`/undo + soft-delete.
- **Стійкість** — Go-клієнт AI робить до 3 спроб на 5xx/мережеві помилки; деградація: бекенд віддає `AI_UNAVAILABLE`, фронт показує повідомлення.

## Комплаєнс (інвестиційні поради)
Системний промт чату забороняє персональні інвестиційні/податкові/юридичні поради й рекомендації конкретних активів; на такі запити — нейтральне пояснення принципу + порада звернутися до ліцензованого фахівця. Будь-яка фінансова порада супроводжується рядком «Це освітня інформація, не індивідуальна інвестиційна порада».

## Рішення щодо prompt-caching
Не вмикається свідомо: префікс (system+tools ≈ 1.5K токенів) менший за поріг кешування Haiku 4.5 (4096 токенів) — кеш не дав би ефекту. Виграш латентності забезпечив перехід на один tool-use виклик замість послідовних router+ReAct.
